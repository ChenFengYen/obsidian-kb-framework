# 知識庫操作指南

## 核心流程

```text
問題 → 搜尋既有筆記 → 回答與缺口 → 提案 → 使用者確認 → 寫入 → 驗證
```

## 新概念

1. 搜尋相同概念、同義詞與既有 MOC。
2. 確認概念能獨立成立，且確實服務目前問題。
3. 提出預計檔名、領域、來源與應連結的筆記。
4. 使用者確認後建立。
5. 將概念放回至少一個合理 MOC；沒有合理入口時先保留為待整理項。

禁止為了消除紅連結自動建立 stub。

## 新來源或論文

1. 保存原始來源與書目資料。
2. 建立 source note；論文使用 citekey 作檔名與連結。
3. 結構化來源的背景、方法、結果、限制與研究關聯。
4. 不自動改寫其他筆記。
5. 當來源被實際研究問題使用時，再把洞見整合進概念筆記或 MOC。

## MOC 維護

MOC 應包含領域敘述、主題分組、跨概念關係、研究切入點與待釐清問題。若只是一串連結，先補上關係說明；若混入大量執行紀錄，將紀錄移到 project/worklog note，MOC 保留導航與判斷。

## 健康檢查

```bash
python OV-Papers/scripts/vault_health.py --summary
python OV-Papers/scripts/vault_health.py --broken-links
python OV-Papers/scripts/note_graph.py
```

- broken link 先分類為真缺筆記、歷史殘留、程式碼誤判。
- orphan 是調查候選，不必全部強行連結。
- 短筆記只有在實際被問題使用時才值得擴充。

## 批次修改安全

1. 先列出檔案、行號、原文與預計修改。
2. 使用者核准後才套用。
3. 小批次執行並檢查 diff。
4. 修改連結後執行 broken-link 檢查。
5. 若指標惡化，停止後續批次並調查。

## 跨機器同步

- 開始工作前先 pull，結束後確認 push 成功。
- 避免兩台機器同時修改同一批筆記。
- 自動同步應有 debounce，避免每分鐘產生提交。
- 原始 PDF、cache 與診斷報告不應進入內容版控。
